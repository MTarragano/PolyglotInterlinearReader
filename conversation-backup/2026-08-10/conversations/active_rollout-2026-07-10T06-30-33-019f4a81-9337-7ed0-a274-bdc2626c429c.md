## Proposed next draft

### 1. Remove the duplicated language controls

I recommend removing the French/Hebrew/Arabic/Turkish button row entirely.

Use one compact active-language selector where a page genuinely needs one:

- Library: its own language filter, defaulting to “All active languages.”
- Import: a required import-language field.
- Reader: derive language from the open text, with a compact text/language switcher if necessary.
- Dictionary: one required language, defaulting to the currently studied language.
- Progress: language filter plus optional “All languages” summary.

The selector should contain only the learner’s selected languages and languages represented by imported texts.

### 2. Support importing a new language

The Import language control should become a searchable selector containing:

- Existing learner/imported languages.
- “Add a new language…”

Adding a language would request only practical defaults:

- Language name and optional ISO code.
- Writing direction: LTR or RTL.
- Script/font preference.
- Generic or language-specific parser/tokenizer, if available.
- Transliteration convention.
- Default interlinear rows.

An unknown or unsupported language should still be importable using generic defaults. It should not require choosing from a country-based master list.

### 3. Turn Import into a review workspace

I recommend a three-stage flow:

1. **Source:** text, audio, URL, date and metadata.
2. **Structure review:** paragraphs and sentence candidates, with split/merge/reorder controls.
3. **Annotation review:** interlinear preview where sentence translations, tokens, transliterations, glosses and morphology can be corrected.

The final stage should show the editable import data and resulting interlinear reader side-by-side, with:

- Back to source.
- Re-run parsing.
- Save draft.
- Confirm import.
- Open in Reader.

This implements your suggestion that import correction and reader preview remain visible together.

### 4. Replace “Known” and the premature 0–100 score

I agree that “Known” suggests a permanent, finished state and should be removed.

For the next prototype, I recommend four understandable stages:

`New → Learning → Acquainted → Well known`

- Up arrow moves one stage higher.
- Down arrow moves one stage lower.
- The Inspector and interlinear token always show the same stage.
- Either action reveals the cloze answer.
- The user can immediately reverse the action.
- Each action records a review event, rather than directly pretending to calculate a scientifically meaningful percentage.

Store encounters, successful/unsuccessful recall, last reviewed and stage separately. A later agreed spaced-repetition method can derive scheduling from that history without losing the original evidence.

### 5. Make Dictionary language-first and word-first

The normal learner view should open with:

- Exactly one language selected.
- Words/lemmas as the default content.
- Recent words as the default scope.

Suggested primary columns:

`Word | Meaning | Learning stage | Frequency | Last seen | Next review | Source text`

Roots, morphemes, grammar features and structural entities should move behind an “Advanced linguistic structure” view. Teachers and administrators could access it more prominently according to later permissions.

Editing should initially distinguish:

- Personal fields: learner note, preferred gloss, learning stage.
- Text-specific corrections: token/lemma/gloss for one imported text.
- Shared dictionary fields: restricted until permissions and provenance are designed.

### 6. Use representative real data

Real fixtures would make the next UI decision much more meaningful. A backend database is not required yet.

I propose extracting your samples into separate fixture files rather than embedding them in `app.js`. A useful first set would be:

- Two or three languages, including at least one RTL language.
- Two to five texts per language.
- Roughly 10–30 sentences per text.
- Sentence translations where available.
- Token, transliteration, lemma, gloss and morphology fields where available.
- Source/provenance metadata.

Missing fields should remain visibly absent—not filled with invented values. Your source files can be JSON, CSV/TSV, spreadsheets, or even structured documents; we can normalize a small subset for the prototype.
